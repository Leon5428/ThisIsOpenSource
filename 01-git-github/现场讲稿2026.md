## 回顾

在上一讲中，我们了解了操作系统的发展历史，什么是开源以及开源的意义，但是现在仍然面临着一个问题，就是如何高效地参与开源项目、管理代码， 以及与其他开发者协作。

我们知道，开源软件允许开发者查看、修改和分享源代码，但是，比如说，现在有一百名开发者正在共同开发一个软件，每个人都可能对源代码进行修改。那么，我们应该如何记录每个人的修改？如何知道某一段代码是谁修改的？如果有人修改代码之后引入了错误，我们又应该怎样恢复到之前的版本？

所以说，我们需要一个强力的工具，这个工具就是Git。

## Git的前世今生

在正式介绍 Git 之前，我们先来了解一下 Git 的诞生背景。

最初开始开发 Linux 的时候，开发者们并没有使用专门的版本控制系统。大家交流代码、提交补丁，主要依靠电子邮件。

具体来说，来自世界各地的开发者会通过电子邮件向 Linux 的创始人 Linus Torvalds 提交自己的代码修改，Linus 则负责审查这些补丁，并将合适的修改整合到自己维护的 Linux 内核代码树中，最后再发布新的内核版本。

但是，这种开发方式存在一个非常明显的问题，那就是代码的版本管理十分困难。

例如，当一个新的 Linux 内核版本发布之后，如果我们想知道这个版本相较于上一个版本究竟修改了哪些内容，就需要借助 `diff` 这样的工具，对两个版本的代码进行比较。

而如果我们想进一步知道某一段代码是谁修改的、为什么要修改，或者希望恢复到之前的某个版本，那么整个过程就会变得更加复杂。

因此，随着软件项目的规模不断扩大，人们逐渐意识到，我们需要一种专门的工具来管理代码的历史版本，这就是版本控制系统。

版本控制系统，英文叫作 Version Control System，简称 VCS，是一种用于记录文件或项目随时间发生的变化，并对这些变化进行管理的工具。

它主要能够帮助我们完成以下几件事情：

首先，记录每一次修改。也就是说，我们可以把项目在不同时间的状态保存下来，形成一系列历史版本。

其次，查看不同版本之间的差异。例如，我们可以知道某次修改增加了哪些代码、删除了哪些代码。

第三，恢复到过去的某个版本。如果某一次修改引入了严重的错误，我们就可以利用版本控制系统找回之前的代码。

第四，追踪修改者以及修改原因。对于每一次提交，我们都可以记录是谁进行了修改，以及这次修改的目的是什么。

最后，也是对于开源项目而言非常重要的一点，就是协调多个开发者共同开发一个项目。即使不同开发者同时修改代码，版本控制系统也能够提供相应的机制，帮助他们整合各自的工作。

所以，版本控制系统实际上解决了软件开发中的一个核心问题：如何有效地管理不断变化的代码，以及如何让多个开发者共同维护同一个项目。

有了版本控制的需求，工具也就跟着出现。2002 年，Linux 内核开发团队开始使用一款名为 BitKeeper 的商业分布式版本控制系统。

BitKeeper 是由 BitMover 公司开发的。当时，BitMover 公司允许 Linux 内核开发社区免费使用 BitKeeper，因此 Linux 开发者得以利用这一工具管理代码，极大地提高了开发效率。

但是，这里存在一个问题：BitKeeper 本身是一款专有软件，并不是自由软件。虽然 Linux 开发者能够免费使用它，但是他们并不能像修改 Linux 内核一样，自由地修改和分发 BitKeeper 的源代码。

于是就有了一个很尴尬的局面：Linux 本身是世界上最著名的开源项目之一，但是开发 Linux 所依赖的版本控制工具却是一款专有软件，而且这款工具的开发公司还能够决定是否允许 Linux 社区继续使用它。

到了 2005 年，BitMover 公司与 Linux 内核开发社区之间发生了矛盾，最终导致 Linux 内核开发社区失去了免费使用 BitKeeper 的权利。

面对这样的情况，Linux 的创始人 Linus Torvalds 决定自己开发一套版本控制系统，以满足 Linux 内核开发的需求。

当然，Linus 并不是想简单地重新实现一个 BitKeeper。他希望新的版本控制系统能够支持大规模的分布式协作，具有足够高的性能，同时保证代码历史的完整性。

于是，2005 年 4 月 7 日，Git 的第一个提交诞生了。

这里值得注意的是，Git 从一开始就是为 Linux 内核这样的大型开源项目设计的，因此它非常重视性能、可靠性以及分布式开发能力。

后来，随着越来越多的开发者开始使用 Git，它逐渐发展成为今天广泛使用的版本控制系统。

至于BitKeeper，在2016 年，BitKeeper正式开源，采用 Apache 2.0 许可证。不过，到了 2020 年，BitKeeper 停止了开发。

## Git的安装

大家可以看到，官网右侧显示了 Git 的最新源代码发布版本，也就是 Latest source release。在它的下方有一个 Install for Windows 按钮，我们点击这个按钮，就可以进入 Windows 版本的下载页面。

点击 Install for Windows 之后，我们就进入了 Git 的下载页面。

大家可以看到，这个页面提供了很多不同的下载选项。

首先，最上方有 Windows、macOS、Linux 和 Build from Source 四个选项，分别对应不同操作系统的安装方式，以及从源代码自行构建 Git。

我们现在处于 Windows 页面，可以看到这里又提供了几个不同的版本。

首先是 Standalone Installer，也就是独立安装程序。其中，x64 Setup 适用于绝大多数使用 Intel 或 AMD 处理器的 Windows 电脑，而 ARM64 Setup 则适用于采用 ARM64 架构的 Windows 电脑。

但是我要说明的是，现在市面上绝大多数Windows笔记本电脑仍然采用Intel或AMD的x86-64处理器，使用ARM架构的Windows笔记本真的不多，可以通过在设置里面找到系统然后查看系统信息，来判断自己是 x86 架构还是 ARM64 架构。

下面还有一个 Portable，也就是便携版本。它与普通安装版的主要区别在于，便携版本通常只需要解压就可以使用，不需要运行传统的安装程序。

对于我们绝大多数同学而言，直接选择Click here to download就可以了。

下载完成之后，我们双击运行 Git 的安装程序，就会进入这个界面。

大家可以看到，安装程序向我们展示了一份 GNU General Public License，也就是 GNU 通用公共许可证，简称 GPL，这里展示的是 GPL 的第二版，也就是 GPLv2。

所以，Git 本身就是一款自由软件，它的源代码是公开的，任何人都可以在遵守许可证条款的前提下使用、修改和分发 Git。

如果你没有听过第一节课，也没关系，这个GPL不会影响我们后续的操作，直接点击 Next，继续安装。

点击 Next 之后，我们就进入了 Git 安装位置的选择界面。

这里的 Select Destination Location，意思就是选择安装位置，也就是我们希望将 Git 安装到电脑的哪个文件夹中。

大家可以看到，安装程序默认选择的是 C 盘下 Program Files 文件夹中的 Git 目录。

如果大家没有特殊需求，直接使用默认的安装路径就可以了。当然，如果不希望将 Git 安装在 C 盘，也可以点击右侧的 Browse 按钮，选择其他安装位置。

另外，大家可以注意到，安装程序在下方提示我们，安装 Git 至少需要大约 342 MB 的磁盘空间。对于现在的计算机来说，这个空间占用并不算大。

这里我就不修改默认的安装位置了，直接点击 Next，继续下一步。

接下来，我们进入了 Git 安装组件的选择界面，也就是 Select Components。

首先是 Additional icons，也就是添加额外的图标。如果勾选下面的 On the Desktop，就会在桌面上创建 Git 的快捷方式。这个选项并不是必需的，大家可以根据自己的喜好选择。

接下来是 Windows Explorer integration，也就是 Windows 文件资源管理器集成。

大家可以看到，这里有两个选项，分别是 Open Git Bash here 和 Open Git GUI here。

勾选之后，我们就可以在文件夹中通过右键菜单直接打开 Git Bash 或 Git GUI。

这里我重点介绍一下 Git Bash。它是 Git for Windows 提供的一个命令行环境，我们后面学习 Git 命令时，主要就会使用这个工具。

而 Git GUI 则是一个图形化工具，可以通过图形界面完成部分 Git 操作。不过，我们这门课主要使用命令行，所以暂时不会使用它。


再往下是 Git LFS，也就是 Git Large File Storage，主要用于管理大型文件。例如，一个项目中包含大量图片、视频或者其他体积较大的文件时，就可能用到它。

下面两个 Associate 选项则与文件关联有关，分别用于关联 Git 配置文件，以及让 Shell 脚本默认通过 Bash 运行。

接下来的 Check daily for Git for Windows updates，用于每天检查 Git 是否存在新版本。

Add a Git Bash Profile to Windows Terminal，则是将 Git Bash 添加到 Windows Terminal 中，方便我们直接通过 Windows Terminal 使用 Git Bash，这个记得选上。

最后还有一个 Scalar，它是 Git 提供的一个用于管理大型代码仓库的辅助工具。对于我们现在学习的这些小型项目来说，基本不会用到，但还是选上吧，没太有影响。

这里顺便说清楚一件事，免得后面产生疑问：Git Bash 不是另外安装的软件，它就在安装包里。后面那一页选 PATH 的时候，选不选都不影响 Git Bash 存不存在。

再往下有一页会让你选 PATH，选了第二项之后，你在 PowerShell 或者 CMD 里也能敲 git。那既然 PowerShell 也能用，为什么课上还要用 Git Bash？

因为变的是外面那一层 shell，不是 git 本身。Git Bash 里能用的是 bash 的语法：ls、cat、cp、rm、grep、find，还有管道、括号取值、单双引号、&& 这些写法。

PowerShell 是另一套语言。ls 和 rm 在它里面只是别名，参数也不一样，比如敲 rm -rf 某个目录，它会直接报错，因为 -rf 不是它的参数。

而开源项目的文档、教程、Issue 里出现的命令，基本都是 bash 写法。大家在 PowerShell 里照着抄，一半会失败，还会以为是自己敲错了。所以这门课的演示统一用 Git Bash，图的就是命令和文档对得上。

点击 Next，继续安装。

接下来，我们进入了 Select Start Menu Folder，也就是选择开始菜单文件夹。

这里需要注意，我们现在选择的并不是 Git 的安装位置，而是 Git 在 Windows 开始菜单中创建快捷方式的位置。

大家平时在 Windows 中点击开始菜单，或者直接搜索某个软件时，就可以通过这些快捷方式找到并启动对应的程序。

这里安装程序默认使用 Git 作为文件夹名称。安装完成之后，我们就可以在开始菜单中找到 Git Bash、Git GUI 等工具。

如果大家希望修改文件夹名称，可以直接在输入框中修改，也可以点击右侧的 Browse 按钮选择其他位置。

另外，左下角还有一个 Don't create a Start Menu folder，也就是不创建开始菜单文件夹。如果勾选这个选项，安装程序就不会创建对应的开始菜单文件夹。

不过，对于我们来说，没有必要修改这些设置，保持默认即可。

这里直接点击 Next，继续安装。

接下来，我们进入了 Choosing the default editor used by Git，也就是选择 Git 使用的默认文本编辑器。

首先，大家可能会有一个疑问：我们不是已经有 Git Bash 了吗？为什么还需要选择一个文本编辑器呢？

这是因为 Git Bash 只是一个命令行环境，而 Git 在执行某些操作时，还需要我们输入或修改文本内容。

例如，我们后面会学习一个叫作 git commit 的命令，它的作用是将代码的修改记录为一次提交。而每次提交时，我们通常都需要填写一段提交说明，用来解释这次修改究竟做了什么。

如果我们执行 git commit 时没有直接指定提交说明，Git 就可能自动打开默认编辑器，让我们输入这些内容。

大家可以看到，这里提供了很多编辑器，包括 Nano、Vim、Notepad++、Visual Studio Code 等。

其中，Vim 是一个非常经典的命令行文本编辑器，功能十分强大，但是对于初学者来说，它的操作方式可能不太容易理解。例如，在 Vim 中输入文字之前，我们通常需要先进入插入模式，而退出编辑器也需要使用特定的命令。

相比之下，Visual Studio Code 对大家来说应该更加熟悉。它提供了图形化的编辑界面，也更符合大多数同学平时编写代码的习惯。

因此，如果大家的电脑上已经安装了 VS Code，我比较推荐选择 Visual Studio Code 作为 Git 的默认编辑器。

当然，如果还没有安装 VS Code，也可以暂时保留默认的 Vim，或者选择其他已经安装的编辑器。这个设置并不是永久不变的，安装完成之后，我们仍然可以通过 Git 的配置命令进行修改，这里选择nano，因为这个操作起来比较简单，然后点击 Next，继续安装。

接下来，我们进入了 Adjusting the name of the initial branch in new repositories，也就是设置新建仓库的初始分支名称。

首先，我们需要简单了解一下什么是分支。

大家可以暂时把分支理解为项目的一条独立开发线路。例如，在开发一个软件的时候，我们可能希望一部分开发者负责添加新功能，另一部分开发者负责修复错误。那么，我们就可以让他们在不同的分支上进行开发，最后再将各自的修改合并起来。

当然，这里只是一个简单的解释，关于分支的具体工作原理和使用方法，我们会在后面专门介绍。

现在大家只需要知道，当我们使用 Git 创建一个新的仓库时，Git 通常会为这个仓库设置一个初始分支名称。

这里有两个选项。

第一个是 Let Git decide，也就是让 Git 自己决定初始分支的名称。在当前安装程序中，这个名称是 master。

第二个是 Override the default branch name for new repositories，也就是由我们自己指定新仓库的初始分支名称。

大家可以看到，这里填写的是 main。

实际上，master 和 main 都只是分支的名称，并没有本质上的功能区别。早期 Git 通常使用 master 作为默认分支名称，而现在很多开源项目和代码托管平台，包括 GitHub，都更倾向于使用 main。

因此，我建议大家选择第二个选项，将初始分支名称设置为 main，这样也更符合目前很多开源项目的使用习惯。

需要注意，这个设置只会影响以后新建的仓库，不会修改已经存在的仓库。

这里我们选择第二项，保持 main 不变，然后点击 Next，继续安装。

接下来，我们进入了 Adjusting your PATH environment，也就是配置 Git 的 PATH 环境变量。

首先，我们需要简单了解一下什么是 PATH。

大家平时在命令行中输入一条命令时，例如 git，操作系统需要知道这个命令对应的可执行程序究竟存放在哪里。

而 PATH 就是一个环境变量，它记录了一系列目录。当我们在命令行中输入某个命令时，系统就可以根据 PATH 中记录的目录，查找对应的可执行程序。

这里安装程序提供了三个选项。

第一个是 Use Git from Git Bash only，也就是只允许我们在 Git Bash 中使用 Git。选择这一项不会修改 Windows 的 PATH 环境变量，因此我们通常无法直接在 PowerShell 或 CMD 中使用 Git 命令。

第二个是 Git from the command line and also from 3rd-party software，也就是允许我们在命令行以及第三方软件中使用 Git。

选择这一项之后，安装程序会将 Git 所需的相关目录添加到 PATH 环境变量中。这样一来，我们不仅可以在 Git Bash 中使用 Git，还可以在 Windows 的 CMD、PowerShell，以及 VS Code 等开发工具中调用 Git。

这也是安装程序推荐的选项。

第三个是 Use Git and optional Unix tools from the Command Prompt。除了 Git 之外，它还会将一些 Unix 工具添加到 Windows 的 PATH 中，例如 find 和 sort。

但是，这里存在一个问题：Windows 本身也提供了同名的命令。如果我们将这些 Unix 工具添加到 PATH 中，就可能导致命令名称冲突，使某些程序的运行结果与预期不同。

因此，对于绝大多数同学来说，我建议选择第二个选项。

这样既能够方便我们在不同的终端和开发工具中使用 Git，又可以避免引入不必要的命令冲突。

这里我们保持第二项不变，点击 Next，继续安装。

接下来，我们进入了 Choosing the SSH executable，也就是选择 Git 使用的 SSH 客户端。

首先，我们需要了解一下 SSH 是什么。

SSH 的全称是 Secure Shell，是一种用于在网络中建立安全远程连接的协议。在使用 Git 的过程中，我们不仅可以通过 HTTPS 与远程仓库通信，也可以通过 SSH 的方式进行通信。

后面我们学习 GitHub 的时候，克隆仓库、推送代码走的都是 HTTPS 这条通道；SSH 是另一种连接方式，这门课不展开。

这里安装程序提供了两个选项。

第一个是 Use bundled OpenSSH，也就是使用 Git 自带的 OpenSSH。选择这一项之后，Git 就会使用随安装程序一起提供的 SSH 客户端，不需要我们额外安装和配置。

第二个是 Use external OpenSSH，也就是使用外部的 OpenSSH。如果我们已经在电脑上安装了 OpenSSH，并且希望 Git 使用系统中已有的 SSH 客户端，就可以选择这一项。

对于我们目前的学习来说，并没有必要进行额外配置，直接使用 Git 自带的 OpenSSH 就可以了。

这样能够保证 Git 使用自己提供的 SSH 客户端，避免因为系统中不同 SSH 客户端的配置差异而产生问题。

因此，我们保持第一个选项不变，点击 Next，继续安装。

接下来，我们进入了 Choosing HTTPS transport backend，也就是选择 Git 使用的 HTTPS 传输后端。

这一页问的是：Git 通过 HTTPS 和远程仓库通信时，用哪个库来校验服务器的证书。

安装程序提供了两个选项。

第一个是 Use the OpenSSL library，使用 OpenSSL 库。选择这一项之后，服务器证书会用安装程序自带的 ca-bundle.crt 文件来校验。

第二个是 Use the native Windows Secure Channel library，使用 Windows 自带的 Secure Channel 库。选择这一项之后，证书会交给 Windows 自己的证书存储来校验，而且它还支持你的组织或学校通过域服务下发的根证书。

对于我们来说，第二个选项通常更方便，因为 Windows 的证书存储和浏览器用的是同一套，如果学校的网络环境里装过根证书，这里也能直接用上。

因此，我们保持第二个选项不变，点击 Next，继续安装。

接下来，我们进入了 Configuring the line ending conversions，也就是配置换行符的转换方式。

在讲这一页之前，我们需要先知道一件事：不同系统里，文本文件的“换行”其实不是同一个东西。

Windows 用两个字符表示换行，一个是回车（Carriage Return，CR），一个是换行（Line Feed，LF），合起来写作 CRLF；而 Unix 和 Linux 只用换行一个字符，写作 LF。

这就带来一个问题：同一份代码，在 Windows 上编辑，可能带的是 CRLF；在 Linux 上编辑，带的是 LF。如果不加处理，整个文件会被认为“每一行都改过”，一次小改动变成了整个文件的改动。

所以 Git 提供了换行符转换的功能，这里给出了三个选项。

第一个是 Checkout Windows-style, commit Unix-style line endings。检出时把 LF 转成 CRLF，提交时再把 CRLF 转回 LF，对应的配置是 core.autocrlf 设为 true，这是 Windows 下的推荐设置。

第二个是 Checkout as-is, commit Unix-style line endings。检出时不转换，提交时把 CRLF 转成 LF，对应的配置是 core.autocrlf 设为 input，这是 Unix 下的推荐设置。

第三个是 Checkout as-is, commit as-is。检出和提交都不做任何转换，对应的配置是 core.autocrlf 设为 false。安装程序的说明里也写了，这个选项不推荐给跨平台的项目。

对我们来说，保持第一个选项就可以了：本地编辑时是 Windows 的习惯，进仓库之后统一存成 LF，别人在 Linux 上拉下来也不会出问题。

点击 Next，继续安装。

接下来，我们进入了 Configuring the terminal emulator to use with Git Bash，也就是选择 Git Bash 使用哪个终端。

第一个是 Use MinTTY，也就是 MSYS2 的默认终端。它支持调整窗口大小、非矩形的文本选择，以及完整的 Unicode 字符。需要注意的是，一些 Windows 控制台程序，比如交互式的 Python，在 MinTTY 里要通过 winpty 才能正常工作。

第二个是 Use Windows' default console window，使用 Windows 自带的控制台窗口。它对 Win32 控制台程序更友好，但默认的回滚行数非常有限，要显示中文等非 ASCII 字符还得自己配置成 Unicode 字体；在 Windows 10 以前，它的窗口也不能自由调整大小，而且只能做矩形选择。

对于我们后面要敲命令、要看大段输出的场景，MinTTY 明显更合适。

因此，保持第一个选项，点击 Next，继续安装。

接下来，我们进入了 Choose the default behavior of git pull，也就是选择 git pull 的默认行为。

git pull 的作用是：把远程仓库的新内容拉到本地，并合进当前分支。当本地和远程各有一些提交的时候，怎么合并就有讲究了，这一页就是让我们选默认用哪一种方式。

第一个是 Merge，合并。它会生成一个新的合并提交，把两条开发线路接起来，保留并行开发的历史，对应的配置是 pull.rebase 设为 false。

第二个是 Rebase，变基。它会把本地的提交挪到远程分支的最新提交之上，让历史保持一条直线，对应的配置是 pull.rebase 设为 true。

第三个是 Fast-forward only，只允许快进。如果没法快进，就直接失败，不会自动合并。

对于我们这门课来说，保持第一个选项 Merge 就可以了，它在出问题的时候最容易看懂发生了什么。

另外，这一页上方还有一行小字，说明现在这个版本的 git pull 总是会先尝试快进。等我们后面讲远程仓库和分支的时候，会再回来解释这一步。

点击 Next，继续安装。

接下来，我们进入了 Choose a credential helper，也就是选择凭据管理器。

我们先说一下“凭据”指的是什么：当我们通过 HTTPS 访问代码托管平台时，需要向服务器证明“我是我”，这就需要账号和访问令牌。如果每次推送都要重新输入一遍，那会很麻烦，所以 Git 可以借助系统的凭据管理器把这些信息存起来。

第一个是 Git Credential Manager，一个跨平台的凭据管理器。选择之后，第一次输入凭据时它会把信息交给 Windows 的凭据管理器保存，之后的操作用 Git 就会自动取用，不用再输入。

第二个是 None，也就是不使用凭据管理器，每次 HTTPS 操作都会重新询问。

安装程序的说明里也写了，只有无图形界面的环境、只用 SSH 的场景，或者要自己接一套凭据管理方案时，才需要选 None。

对于我们来说，保持第一个选项 Git Credential Manager，点击 Next，继续安装。

接下来，我们进入了 Configuring extra options，也就是配置一些额外选项。

第一个是 Enable file system caching，启用文件系统缓存。Git 会把文件系统的信息成批读进内存缓存起来，对应的配置是 core.fscache 设为 true，在处理比较大的仓库时性能提升比较明显。

第二个是 Enable symbolic links，启用符号链接。这个选项需要系统允许创建符号链接，通常要有管理员权限，而且它只对之后新建的仓库生效。

对于我们现在的学习来说，保持默认就好：第一个勾上，第二个不勾，然后点击 Install，开始安装。

最后，我们进入了 Completing the Git Setup Wizard，也就是安装完成界面。

下面有两个勾选框：Launch Git Bash 表示装完立刻打开 Git Bash，View Release Notes 表示打开这次的发行说明。这两个选不选都不影响后面的使用。

点击 Finish，安装程序就关闭了，Git 也就装好了。

## Git配置

Git 装好了，但还不能马上用。在第一次提交之前，我们必须先告诉 Git 一件事：你是谁。

为什么要这样？因为版本控制记录的不只是“改了什么”，还包括“是谁改的、什么时候改的”。每一次提交，Git 都会把作者的姓名和邮箱写进提交记录里，以后用 git log 看历史的时候，这些信息会跟着一起显示出来。

所以接下来要做的是配置提交者的姓名和邮箱，一共两条命令。

第一条是 git config --global user.name “你的用户名”，第二条是 git config --global user.email “你的邮箱”。

这里的 --global 表示这条配置对当前用户在本机上的所有仓库都生效，配置内容会被写进用户目录下的 .gitconfig 文件里，在 Windows 上通常是 C 盘用户目录下的 .gitconfig。如果我们不加 --global，这条配置就只对当前这个仓库生效，写在仓库里的 .git 目录下的 config 文件中。

姓名填你希望大家看到的名字。

邮箱建议填你以后要用来注册代码托管平台的那个邮箱。因为平台是靠邮箱把提交记录和你的账号对应起来的，填错了，平台上的提交就不会算到你名下。

配置完成之后，我们可以用 git config --global --list 查看当前生效的所有配置，确认刚才那两条都已经写进去了。

## Git的基本工作原理

装好、配置好之后，我们就可以开始用 Git 了。但是在敲命令之前，我们要先弄清楚 Git 是怎么组织一个项目的，否则后面每一条命令都只能靠背。

第一件事是“仓库”。

当我们在一个项目文件夹里执行 git init 命令的时候，Git 会在这个文件夹下面创建一个名为 .git 的目录，这个目录里存放着版本控制需要的全部信息。从这一刻起，这个普通的文件夹就变成了一个 Git 仓库。

这里有一点需要说明：git init 并不要求这个文件夹是空的。如果你已经写了一些文件，直接在里面执行 git init 就可以，原有文件既不会被删除，也不会被修改，它们只是从“没人管的文件”变成了“Git 可以跟踪的文件”。

我们再单独看一下 .git 这个目录。

它是一个以点开头的目录，在 Windows 下会被标记成隐藏目录，所以在资源管理器里默认是看不到的，需要打开“显示隐藏的项目”才能看到。

里面放的是版本控制的核心数据：objects 目录存放被 Git 记录下来的内容，refs 目录和 HEAD 文件记录当前在哪个分支上，config 是这个仓库自己的配置，hooks 和 info 则是一些辅助脚本和说明。另外还有一个 index 文件，也就是暂存区的状态，这个文件要等到第一次 git add 之后才会出现。

现在大家只需要记住两件事：这个目录里的东西不要手动去改；也不要在没有备份的情况下直接把它删掉，因为删掉 .git 就等于删掉了这个项目的全部历史。

接下来是“工作区”。

工作区就是我们实际看到、实际编辑的那些文件。你打开编辑器，修改某个文件，保存，这个改动就发生在工作区里。

换句话说，工作区是“你手头正在用的那一份”，它和 Git 里保存的历史可能是不同的。你改了文件但还没有告诉 Git，这个改动就只存在于工作区里，Git 并不知情。

第三个概念是“暂存区”。

当我们在工作区改完文件之后，用 git add 命令，就能把指定文件的新增、修改或者删除这些变化放进暂存区。

需要强调的是，暂存区并不是一个能在文件夹里打开的普通目录，它更像是一份“待提交清单”：你在告诉 Git，“这些改动，我下一次提交的时候要带上”。它的状态记录在 .git/index 这个文件里。

暂存区是初学者最容易糊涂的地方。它存在的意义其实很简单：你一次可能改了好几个文件，但这一次提交只想带上其中两个，暂存区就给了你这个选择。

最后是“版本库”。

当我们执行 git commit 命令，Git 就会根据暂存区里的内容创建一次新的提交（Commit），记录下项目在这一刻的状态，并把相应的版本信息保存在 .git 目录中。

每一次提交都有一个唯一的标识符，也就是提交的哈希值，它是一串很长的字符，用来唯一地指认这一次提交。以后如果想看过去都提交了什么，就用 git log 命令把提交历史列出来。

到这里，三个概念就串起来了：工作区是你手头正在用的文件，暂存区是下一次提交要带上的清单，版本库是已经存下来的历史。修改、暂存、提交，就是在这三者之间来回移动。

下面我现场演示一遍，大家重点看 git status 的输出是怎么随着操作变化的。

我会先在一个空文件夹里执行 git init，然后新建一个文件、写一点内容，用 git status 看 Git 怎么说；再 git add，再用 git status 看有什么变化；然后 git commit 提交；最后用 git log 看历史里多出来的这一条。

## 演示一

新建一个文件夹 MyProject2，在里面新建文本文件 file1.txt，随便写点内容。

执行 git init，会输出 Initialized empty Git repository in 加路径。打开「显示隐藏的项目」，能看到多出来的 .git 目录。

执行 git status，输出 On branch main 和 No commits yet，下面一段 Untracked files 列着 file1.txt，意思是 Git 还没开始跟踪它。

执行 git add file1.txt，这一步没有输出。

再执行 git status，这次显示 Changes to be committed，下面一行 new file: file1.txt，说明它进了暂存区。

执行 git commit -m "新增 file1.txt"，输出里会出现 1 file changed，提交成功。

执行 git log，能看到这一次提交：commit 后面是哈希，Author 是配置的名字和邮箱，下面是刚才写的说明。提交多了会进入分页，按 q 退出。

## Git的基本操作

把刚才演示的过程归纳一下，就是这一页上的四条命令。

git status 用来看当前工作区和暂存区的状态，也就是“我改了什么、哪些已经 add 了”。

git add 文件名 用来把指定文件的变化加入暂存区。

git commit -m “提交说明” 用来把暂存区里的内容记录成一次提交，-m 后面跟的是这次提交的说明，用来解释这次到底改了什么。

git log 用来看过去的提交记录。
提交说明也不是随便写的。它要让别人一眼看懂这次改了什么：一行说清目的，比如“给 file1.txt 加一行”，不要写“更新”“修改”这种什么都没说的词。以后你在 PR 里、在历史里看到的，全是这些说明。

这就是一次完整的提交：改文件，用 git add 放进暂存区，用 git commit 提交。

这里需要强调的是：暂存区决定了下一次提交包含哪些修改。只有放进暂存区的修改才会被提交，如果你的修改只是放在了工作区而没有添加到暂存区，是不会被提交的。

## git status 命令

### 第一页：未跟踪

git status 用来看当前工作区和暂存区的状态，说白了就是查看一下现在走到哪一步了。

比如说我们在工作区里新加了一个文件 file2.txt。

这时候 Git 会显示 Untracked files，下面列着的就是这个 file2.txt。

未跟踪的意思是：这个文件虽然已经放在仓库的文件夹里，但仅仅存在于工作区，Git 还没有开始跟踪它，你改它、删它，Git 都不会记录。

下面括号里那一行是 Git 给的提示，告诉你可以用 git add 把它加入暂存区。

最后一行 nothing added to commit but untracked files present，说的是现在没有可以提交的内容，只有未跟踪的文件。

所以要把这个文件纳入版本控制，第一步就是 git add。

### 第二页：已修改、未暂存

file1.txt 是之前已经提交过的文件，我们在工作区里改动了它。

这时再看 git status，输出里最上面那段 Untracked files 还在，因为 file2.txt 一直没有被 git add。

下面多出来一段，是 Changes not staged for commit，意思是“已经改动、但还没有放进暂存区的变化”，下面列着的就是 modified 的 file1.txt。

注意这里是 modified，和上一页的 untracked 不是一回事。区别在于：Git 已经开始跟踪 file1.txt，所以知道它被改过，也能比较出改动内容；而 file2.txt 是新文件，Git 对它还一无所知。

这一段下面同样有提示，告诉你可以用 git add 把改动放进暂存区。

最后一行 no changes added to commit，说的是现在暂存区还是空的，这些改动都还没准备好被提交。

### 第三页：已暂存

这一页里，两个文件都被放进了暂存区。截图里用的是 git add 后面加一个点，这个点表示当前目录下的所有改动，比逐个写文件名省事。

再执行一次 git status，输出里只剩一段 Changes to be committed，意思是“等待被提交的改动”。

上一页那两段都不见了：Untracked files 和 Changes not staged for commit 都消失了，因为 file2.txt 和 file1.txt 的改动现在都已经在暂存区里。

下面两行的前缀不同：modified 表示这是一个被改动的旧文件，new file 表示这是一个新文件。

括号里的提示也从 git add 变成了 git restore --staged，意思是如果你后悔了，可以用它把文件从暂存区移出去。

我们下面来演示一下这个命令。

## 演示二

接着刚才那个仓库，新建文件 file2.txt，随便写点内容。

执行 git status，Untracked files 下面列着 file2.txt。

打开 file1.txt 改几行并保存，再执行 git status。这次输出分成两段：上面是 Changes not staged for commit，里面 modified: file1.txt；下面是 Untracked files，里面 file2.txt。

## git log 命令

git status 看的是现在，git log 看的是过去。它把提交历史按时间倒序列出来，最新的一次排在最上面。

一次提交显示成一块。第一行 commit 后面那串是这次提交的哈希，用来唯一标识它；下面 Author 是作者，Date 是提交时间；空行下面那一句是提交说明，也就是当初 git commit -m 写的内容。

提交多了以后，完整信息一屏放不下，这时候用 git log --oneline。它一行一条，只留哈希的前 7 位和提交说明，作者、时间都不显示。

哈希只留 7 位不是随便定的，同一个仓库里 7 位基本不会重复，区分提交够用了。

第一次用完整版 git log 的人，经常会以为程序卡住了：屏幕上不出字了，最下面还多了个冒号。那是一个分页器，按空格翻页，按上下方向键一行一行看，按 q 退出回到命令行。

## git amend命令

有时候刚提交完就发现不对：要么漏了一个文件没加进去，要么提交说明写错了。这时候不用再另外提交一次，用 git commit --amend 就能改掉最近这一次。

如果只是漏了文件，先把漏掉的那个文件加入暂存区，再执行 git commit --amend。它会用暂存区里的内容重新做一次提交，把刚才那一次替换掉。

注意这里是“替换”而不是“追加”：历史里不会多出一条，看起来就像你第一次提交的时候就把这个文件带上了。

如果只是提交说明写错了，文件不用动，直接 git commit --amend 后面加 -m，写上新的说明就行。

要是不加 -m，它会打开编辑器，把上一次的说明调出来让你改，保存退出之后才生效。

最后是两条限制。第一，amend 只能改最近一次提交，再往前的就得用 git reset。

第二，它会生成一个新的提交，哈希值会变。也正因为如此，这个命令只能在自己本地用，已经推到远程的提交不要这样改。

## 演示三

先把暂存区里的东西提交掉：执行 git commit -m "新增 file2.txt，修改 file1.txt"，输出 2 files changed。

这时候发现漏了一个文件，新建 file3.txt 写点内容。执行 git status，它在 Untracked files 里。

执行 git add file3.txt，再执行 git commit --amend，这一次不加 -m。

Git 会打开编辑器（安装时选的是 nano），把上一次的提交说明调出来。在末尾补一句，按 Ctrl+O 保存、回车确认，再按 Ctrl+X 退出。

退出后执行 git log，历史里仍然只有两条提交，没有变成三条，说明 amend 是替换不是追加。

再演示改说明：执行 git log --oneline 记下最新那条的哈希；执行 git commit --amend -m "新增 file3.txt"；再执行 git log --oneline，说明变了，哈希也变了。

## git restore 命令

刚才是改提交，这一页是改文件：还没提交的改动，怎么退回去。

两条命令长得很像，只差一个 --staged。

第一条 git restore 后面跟文件名，作用是丢弃工作区里还没 add 的修改。也就是说，你改了文件但还没 git add，执行它，文件就回到暂存区里的那一份，刚才改的东西没有了。所以这条要慎用，写好的内容说没就没。

第二条 git restore --staged 后面跟文件名，作用完全不同：它只是把文件从暂存区拿出来，文件本身的改动还在，一个字都没丢，相当于撤销了刚才那次 git add。

所以可以把这两条理解成两级操作：先用 --staged 把“加入暂存区”这一步撤掉，再决定要不要用第一条把改动本身扔掉。

最后一句要注意范围：这两条都只对还没提交的内容有效。已经提交的东西，restore 管不了，那就得用下一页的 reset。

## 演示四

打开 file1.txt 改几行并保存。执行 git status，它在 Changes not staged for commit 里，modified: file1.txt。

执行 git restore file1.txt，没有输出。再执行 git status，输出变成 nothing to commit, working tree clean。打开文件看，内容回到了上一次提交的样子。

再改一次 file1.txt，执行 git add file1.txt，再 git status，它出现在 Changes to be committed 里。

执行 git restore --staged file1.txt，没有输出。再 git status，它又回到 Changes not staged for commit；打开文件看，刚才改的内容还在。

最后执行 git restore file1.txt，把这次改动也丢掉，git status 回到干净状态。

## git reset 命令

上一页的 restore 管不到已经提交的内容，这一页的 reset 就是用来处理这些内容的。

git reset 的作用是把当前分支退回到指定的那一次提交。指定哪一次都可以，不限于上一次。

写法有两种：一种是直接写提交的哈希，比如 9c1b2ab；另一种用相对位置，HEAD~3 表示往前退三次。HEAD~ 是“上一次”的简写，HEAD~3 就是三次之前的那次提交。

重点是三种模式，它们的差别只有一句话：退回之后，那些改动还在不在。

--soft 最温和：提交退回去，改动留在暂存区。等于把提交拆掉，但内容都还在，随时可以重新提交。

--mixed 是默认模式：提交退回去，改动从暂存区退到工作区。文件和刚才一样，只是要重新 add 一遍。

--hard 最彻底：提交退回去，改动一起删掉，没有后悔的余地。所以执行之前，先用 git log 把当前的哈希记下来。

一句话记法：soft 连暂存区都留着，mixed 只留工作区，hard 什么都不留。

## .gitignore 文件

不是所有文件都需要进仓库。编译产生的日志、程序运行留下的临时文件、编辑器自己生成的缓存，这些保存下来没有意义，反而会把提交记录搅乱。

.gitignore 就是用来列这些文件的地方。写在里面的规则，Git 会直接忽略，git add 也不会把匹配的文件加进来。

规则写法看页面上这几行。井号开头是注释，整行都不算数；*.log 匹配所有以 .log 结尾的文件，不管它在哪个目录；build/ 后面带斜杠，表示忽略整个目录以及里面的内容；/todo.txt 前面带斜杠，表示只匹配仓库根目录下的这一个，子目录里的同名文件不受影响；!important.log 开头加感叹号表示例外，前面那些规则对它不生效。

然后要注意下面那句“但是”：一个文件如果已经被提交过，之后再把它写进 .gitignore 也没用，Git 照样继续跟踪它。想让它真正消失，得先把文件从仓库里删掉，再提交一次。

最后补一句：.gitignore 本身是要提交进仓库的，不然别人克隆下来就没有这套规则。

## 什么是分支

所谓分支，就是从某一次提交上分出去的另一条提交线路。

一个仓库刚开始只有一条线，就是 main。

再看图上这两行。上面一行是 main；下面这一行，就是我们从 C 这个提交上分出去的另一条线，叫 feature。

前面 A、B、C 三个提交，两条线共用，因为 feature 是从 C 分出来的，而不是复制了一份。

分出去之后，在 feature 上又提交了一次，就是 D。这次提交只加在下面这一行，main 还停在 C。

下面这三条说的是切换的效果。切到 feature，工作区里的文件就是 A、B、C、D 一路改下来的结果；切回 main，文件又变回 C 的样子，D 带来的改动看不到。

两条线上的提交互不干扰，各自只记在自己那条线上。

## 为什么需要分支

知道分支是什么之后，接下来是为什么需要它。

先说一个常见的情况：手上的代码是能跑的，现在要给代码加一个新功能。

麻烦出在中间状态上。功能写到一半，代码是残缺的。这时候直接提交到主干，就把能用的版本弄坏了；可不提交，已经写好的部分又留不住。

分支正好能解决这个矛盾：在主干之外另开一条线，新功能就在那条线上写。

好处就是页面上列的这三条。

第一，主干照旧可用，别人该干什么干什么，不受到你的影响。

第二，新功能那条线上可以随便提交，哪怕中间的提交是坏的也不要紧，反正没人用那条线。

第三，写完了把这条线合回主干；要是写废了，直接把这条线扔掉，主干从头到尾都没被碰过。

一句话：分支让主干始终保持是“能用的那一份”。

## 分支是一条指针

上一页说分支是另开一条线。那这条线在 Git 里究竟是什么？答案是一个指针：它指向某一次提交。

所以说它并不是把文件复制一份。新建一个分支，仓库里不会多出第二份代码，只是多了一个名字，指向某个已经存在的提交。

正因为没有复制，创建分支几乎不占空间，也非常快，一秒钟能建好几条。

然后是下面这个词，HEAD。HEAD 是 Git 用来记录“你现在在哪条分支上”的一个标记。

它指向哪条分支，你就在哪条线上。你提交的时候，新的提交是加到 HEAD 所指的那条分支上。

所以切换分支，本质上就是让 HEAD 指向另一个指针。

HEAD 一变，工作区里的文件也跟着变，变成那条分支上本来的样子。

## 创建与切换分支

这一页是四条常用命令，一条一条说。

第一条 git branch，后面不加任何参数，作用是列出所有分支。当前所在的那条，前面会有一个星号。

第二条 git switch -c 加分支名，新建一条分支，并直接切换过去。-c 是 create 的缩写。执行完这条，HEAD 就指到新分支上了。

第三条 git switch 加分支名，切换到一条已经存在的分支，比如切回 main。

第四条 git branch -d 加分支名，删除一条分支。d 是 delete。默认只能删已经合并过的分支，没合并的会被拒绝，这是防止误删的保护。

这四条可以按动词记：switch 管切换，branch 管分支本身，列出、新建、删除都是它。

## 合并分支

分支写完了，最后要合回主干，用的是 git merge。

这里有一点最容易搞反：**先切换回那条要接收改动的分支**，也就是 main，再执行 git merge，后面跟要合并进来的分支名。

所以是两行命令：先 git switch main 切回主干，再 git merge feature，把 feature 合进 main。

合并的结果有两种，取决于这段时间两条线各自有没有往前走。

第一种是快进。如果从分出去那一刻起，main 上一个新提交都没有，那就说明 main 只是落后于 feature，Git 会把 main 直接挪到 feature 的最后一个提交上，像快进一样，不会多出提交。

第二种是合并提交。如果两条线都各自提交过，谁也追不上谁，Git 就会生成一个新的提交，把两条线接起来。这个提交有两个父提交：一边是 main 之前的最后一个，一边是 feature 的最后一个。

一句话：能快进就快进，不能快进就造一个合并提交。

## 解决冲突

合并大多数时候是自动完成的。什么时候才会出问题？就是两条分支碰巧改了同一个文件的同一处。

Git 判断不了应该听谁的，就把两边的内容都写进文件里，停下来让你决定。

打开文件，会看到页面上这样一组标记。

第一行 <<<<<<< HEAD 是开头，到 ======= 这行为止，中间是**你当前所在这条分支**上的内容。

======= 到 >>>>>>> feature 这一段，是**要合进来的 feature** 上的内容。

解决就三步。

第一步，想清楚最终要成什么样，把内容改成那个样子，然后把这三行标记全删掉，一行都不要留。

第二步 git add，告诉 Git 这个文件已经处理好了。

第三步 git commit，完成这次合并。这时 Git 会带着一段默认的提交说明，直接保存就行。

## 演示五

先执行 git branch，输出一行 * main。

执行 git switch -c feature，输出 Switched to a new branch 'feature'。再执行 git branch，星号跑到 feature 上。

打开 file1.txt 加一行并保存。执行 git add file1.txt，再执行 git commit -m "在 feature 上加一行"，输出 1 file changed。

执行 git switch main，输出 Switched to branch 'main'。打开 file1.txt，刚才加的那行不在了，因为那次提交只在 feature 上。

这一步最容易出错：如果忘了 commit 就切分支，Git 会把改动带过去，屏幕上会多出一行 M file1.txt。看到这一行就说明改动还没提交，切过去的不是干净的主分支。所以切之前先 git status，输出是 clean 再切。

接着演示快进：main 上没有新提交，执行 git merge feature，输出里会出现 Fast-forward 和 1 file changed。打开 file1.txt，刚才那行回来了。执行 git log --oneline，只有三条提交，没有多出合并提交。

再演示合并提交：在 main 上打开 file2.txt 改一行并提交；执行 git switch feature，打开 file3.txt 改一行并提交。这两次切换前 git status 都是干净的，不会再出现 M.

切回 main，执行 git merge feature，会弹出编辑器让你确认合并提交的说明，保存退出后 git log --oneline 里多出一条新提交。

最后演示冲突：确认当前在 main 上，打开 file1.txt 把刚才那行改成别的内容并提交；执行 git switch feature，打开 file1.txt 把同一行改成第三种内容并提交。

切回 main，执行 git merge feature，输出里会出现 CONFLICT，并列出冲突的文件。

打开 file1.txt，能看到 <<<<<<< HEAD、=======、>>>>>>> feature 这些标记。把它改成最终想要的样子，标记全部删掉。

执行 git add file1.txt，再执行 git commit，默认说明保存即可。git log --oneline 里能看到这次合并提交。

## GitHub 是什么

前面讲的全是 Git，都在你自己电脑上。从这一页开始是 GitHub。

要先分清这两个东西。Git 是装在你电脑上的版本控制工具，负责记录提交历史；GitHub 是一个网站平台，负责把这些仓库放到网上。

所以它们不是一回事，也不是同一个东西的两种叫法。没有 GitHub，Git 一样能用，只是仓库只能待在你自己的电脑里。

GitHub 能做的事就是页面上这句：把本地仓库放到互联网上，别人就能看到、能下载、能提意见，甚至直接帮你改。

一句话记：Git 管版本，GitHub 管人和协作。

那 GitHub 到底重要在哪？

第一，它现在是开源世界的事实中心。你能想到的很多项目，源码就放在上面：Python 的实现 CPython、VS Code，Linux 内核在那边也有镜像。想找某个库、想看某个工具是怎么实现的，第一站基本都是 GitHub。

第二，它把协作的流程固定了下来。以前给开源项目贡献代码，靠的是邮件列表加补丁文件，来回几封邮件才说得清一件事。GitHub 把这套流程搬到了页面上：Issue 里讨论，Pull Request 里看改动，Review 里逐行提意见，最后点一下合并。所有人看的是同一个页面，不用再翻邮件。

第三，它把参与门槛降了下来。你不需要是项目成员，也不需要谁给你开权限。注册一个账号，fork 一份，改完提 PR，项目维护者就能看到你的改动。这是以前很难做到的事。

第四，它把贡献留成了公开记录。你的提交、你的 PR、你参与过的讨论，都挂在账号下面，谁都能看。对初学者来说，这比简历上写一句“熟悉 Git”有说服力得多。

所以 GitHub 不只是“把仓库放到网上”，它改变了一群人在互联网上一起写软件的方式：谁都可以提，谁都可以看，改动有痕迹，讨论留得住。

再回到页面上这句：它把本地仓库放到互联网上，别人就能看到、能下载、能提意见，甚至直接帮你改。

一句话记：Git 管版本，GitHub 管人和协作。

## 新建一个仓库

GitHub 上得先有一个仓库，本地的东西才有地方推。这一页看怎么建。

登录之后点右上角的加号，选 New repository，就进到这个页面了。

第一部分是 General。Owner 是这个仓库归谁，一般就是你自己；Repository name 是仓库名，页面上会建议起短一点、好记一点的名字；Description 是描述，可以先不填。

第二部分是 Configuration。Choose visibility 是选公开还是私有：公开的话所有人都能看到这个仓库，私有的只有你自己和被你加了权限的人能看。这门课用公开就行。

下面还有三个开关，Add README、Add .gitignore、Add license。这三个先都不选，等我们自己把文件推上去的时候再放，不然仓库一建好就自带一次提交，后面会多一步。

最后点绿色的 Create repository，仓库就建出来了。

建好之后，页面上的那个 https 地址就是它的远程地址，下一页 clone 要用到它。

## 克隆到本地

GitHub 上建好的那个仓库现在是空的，得把它拿到本地来干活。

用的是 git clone，后面跟上仓库的地址，就是上一页看到的那个 https 链接。

这条命令做两件事：一是把这个仓库完整下载到本地，二是自动把这个远程地址记下一个名字，叫 origin。

origin 就是“远程仓库”的默认名字。以后 push、pull 都直接用它，不用每次都把完整地址写一遍。

下面这个块讲 clone 和 init 的区别，这两个别搞混。

git init 是从零开始建一个空仓库，里面什么都不带，你之前的提交历史也没有。

git clone 是把远程已经存在的仓库连历史一起拿下来。拿下来就是一个完整的仓库，之前所有提交都在里面。

所以 clone 下来的仓库不用再执行 git init，它本身已经是仓库了。

## 把本地提交推上去

前面做的一切都在本地。commit 之后，历史只存在你自己的电脑上，GitHub 上那个仓库还是空的。

push 就是把本地的提交送到远程仓库去。它送的是提交，Git 会把这些提交需要的数据打包传上去。

命令是 git push，后面跟上远程仓库名和分支名。第一次推的时候建议加 -u。

-u 是 set upstream 的意思，它会在推完之后多记一件事：把本地这条分支和远程的同名分支关联起来。

关联起来的好处是，以后再推就不用写后面那一串了，直接 git push 就行；拉的时候也一样，直接 git pull。

## 演示六

在 GitHub 上打开刚建好的仓库，点绿色的 Code 按钮，复制那个 https 地址。

在本地找一个目录，执行 git clone 加上地址。因为仓库是空的，输出里会有一行 warning: You appear to have cloned an empty repository.

cd 进这个目录。执行 git status，输出 On branch main 和 No commits yet。

执行 git branch -a，什么也不打印，因为还没有任何提交，也就没有分支。

新建一个文件，执行 git add . 和 git commit -m "第一次提交"，输出 1 file changed。再执行 git branch，这次能看到 * main。

这一步不能省：后面要推的就是这次提交。如果没提交就 push，Git 会提示 Everything up-to-date，GitHub 上什么都不会出现。

执行 git branch -a，能看到 main 和 remotes/origin/main。执行 git branch -vv，main 后面跟着 [origin/main]，说明对应关系在 clone 的时候就建好了。执行 git remote -v，输出两行，都是 origin，指向刚才那个地址。

顺便讲清楚 clone 替我们做的两件事：一是把远程地址记下来，起名 origin；二是把本地 main 和远程 main 对应起来，这个关系叫 upstream。

这里把登录的事说清楚：克隆公开仓库不需要登录；遇到私有仓库，或者第一次 push，Git 会弹出 Connect to GitHub 的窗口。默认是 Browser/Device 这一页，点 Sign in with your browser，浏览器里点 Authorize 就完成。旁边还有 Sign in with a code，适合没有浏览器的机器；上面还有一个 Token 页签，是把 Personal access token 粘进来。课上用第一种就够。token 等同于密码，不要写进代码，也不要提交到仓库。

执行 git status，确认输出是 nothing to commit, working tree clean。

执行 git push，会弹出登录窗口，授权完成后输出里出现 * [new branch] main -> main，说明推上去了。

刷新 GitHub 页面，能看到刚才那次提交和那个文件。

再改一个文件、提交，然后只敲 git push，输出里会显示这次提交已经推上去，不会再出现 [new branch] 那一行。

最后把这件事反过来看一遍：换成从 git init 开始的本地仓库会怎样。新建一个文件夹，执行 git init，建一个文件、提交一次。

执行 git push，会报 fatal: No configured push destination.，意思是不知道该推到哪去，下面提示用 git remote add 配置远程。

执行 git remote add origin 加上远程地址，再执行 git push，这次报 The current branch main has no upstream branch.，下面提示用 git push --set-upstream origin main。

执行 git push -u origin main，这次成功，并打印 branch 'main' set up to track 'origin/main'.，这一行就是对应关系建好的标志。

## 远程仓库也有分支

远程仓库里不只是 main，还可能有别的分支，比如 feature。

clone 或者 fetch 之后，每一个远程分支都会在本地留下一个只读的副本，名字前面带 origin/，比如 origin/main、origin/feature。

它们只是“远程当时长什么样”的本地快照，不是能往上提交的分支，所以不能直接改 origin/xxx。

想看有哪些远程分支，用 git branch -r；想连本地的一起看，用 git branch -a。

## 本地分支和远程分支怎么对上

本地和远程的分支，关系有两种情况。

第一种是本地有、远程没有。比如你自己用 git switch -c 新开的 feature，远程还看不到它。第一次推的时候用 git push -u origin feature，Git 会在远程建出同名分支，并把两边关联起来。

第二种是远程有、本地没有。比如别人推到远程的 feature。这时候不需要 push，切一下就行：git switch feature，Git 会依据本地已有的 origin/feature，建出一条同名本地分支并跟踪它。

注意第二种的前提：本地得有 origin/feature 这个快照。没有的话，要先 fetch。

## 演示七

执行 git switch -c feature，输出 Switched to a new branch 'feature'。改一个文件并提交，输出 1 file changed。

这时候到网页上看，仓库里看不到 feature。

执行 git push -u origin feature，输出里会出现 * [new branch] feature -> feature 和 branch 'feature' set up to track 'origin/feature'.

执行 git branch -r，能看到 origin/feature 出现了。

换一个文件夹重新 clone 这个仓库，执行 git branch -a，本地只有 main，远程那边有 origin/main 和 origin/feature。

执行 git switch feature，Git 会自动建出本地 feature 并切过去，输出里会提到 set up to track 或者 up to date with 'origin/feature'。再执行 git branch -vv，feature 那行后面跟着 [origin/feature]。

## 本地分支 & 远程分支

还有一种情况：clone 的时候远程并没有 xxx 分支，是克隆之后才有人推上去的。

这时候本地连 origin/xxx 这个快照都没有，直接 git switch xxx 会报错说找不到。

正确的顺序是先 git fetch。它把远程各个分支的新提交都下载下来，更新本地的 origin/*，你自己的分支和工作区都不动。

fetch 完成之后，origin/xxx 就有了，再执行 git switch xxx 就能建出对应的本地分支。

## 演示八

回到演示六那个仓库。在网页上再新建一条分支 dev。

本地执行 git branch -r，输出里没有 origin/dev。

直接执行 git switch dev，会报错 fatal: invalid reference: dev.

先执行 git fetch，再执行 git branch -r，origin/dev 出现了。

再执行 git switch dev，这次成功。git branch -vv 里能看到它跟踪 origin/dev。

## 个人使用 ⇒ 团队合作

前面这些操作，一个人用完全够了：自己写、自己提交、自己推。

但多人一起写同一个仓库，就要有规矩，不然仓库很快就乱了。

页面上这五步是组内协作的基本流程：建仓库加协作者、按任务开分支、在分支上写并推上去、提 PR、通过后合并。

第二步值得多说一句：分支是按任务分的。一个功能一条分支，几个人可以共用一条，而不是一个人一条。

## 演示九

先用 A 账号打开仓库，进 Settings，找到协作者那一项，点添加，输入 B 的 GitHub 用户名，权限选 Write，确认。添加成功后，列表里会出现 B 的名字。

B 登录自己的账号，在通知里收到邀请，点接受。接受之后，B 也能在首页看到这个仓库。

B 把它 clone 到本地，执行 git branch -a，能看到远程那几条分支。

clone 下来工作区默认停在 main 上，所以 B 先执行 git switch 到自己负责的那条分支，再开始改。

改完提交、push，A 刷新仓库页面就能看到 B 推上去的提交。

最后补一句：A 随时可以在同一个页面把 B 移出协作者，移出之后 B 再 push 会被拒绝，提示没有权限。

## 把远程的改动拉下来

别人推了新提交，你本地还是旧的，这就用 git pull。

pull 做两件事：把远程的提交取回来，然后合并到你当前所在的分支。

它和 fetch 的区别在于合不合。fetch 只下载，把远程各个分支的新提交拿下来、更新 origin/* 这些快照，但不碰你的分支，也不改工作区。

pull 等于 fetch 加 merge：下载完立刻合并，工作区里的文件马上跟着变。

所以想先看看再决定，用 fetch；确定要合，用 pull。

## 演示十

先制造一个别人推了新提交的场景：用另一个账号，或者直接在网页上改一个文件并提交，远程就多了一次提交。

回到本地，执行 git log --oneline，最新一条还是原来那次。

执行 git fetch，输出里会列出取到的内容。再执行 git log --oneline origin/main，能看到远程那次新提交。

这时候执行 git log --oneline，本地 main 还是旧的；打开文件看，工作区也没变。这就是 fetch 只更新快照。

执行 git merge origin/main，本地 main 才追上，文件跟着变。

再试一次 pull：让远程再提交一次，本地直接 git pull，输出里会显示 Fast-forward，这一步把下载和合并一起做完了。

## 推送被拒绝怎么办

push 有时候会被拒绝，最常见的原因是你落后了：别人先推了提交，本地还是旧的。

Git 提示 non-fast-forward，意思是你这条线接不上远程那条线，它不会替你覆盖别人。

处理办法就是先 pull，把远程的提交合并进来。

绝大多数情况下合完就结束了，Git 自动合上，不用你动手。

只有两边改了同一个文件的同一处，才会停下来让你手工解决冲突。

解决完再 push 就正常了。不要用强推绕过它，那会把别人的提交冲掉。

## 演示十一

先在网页上把 file1.txt 的某一行改掉并提交；同时本地把同一行改成别的内容，也提交。

执行 git push，会被拒绝，输出里是 ! [rejected] main -> main (fetch first)，意思是远程有你本地没有的提交。

执行 git pull，会报 CONFLICT，并列出冲突的文件。

打开那个文件，能看到 <<<<<<< HEAD、=======、>>>>>>> 三段标记。把它改成最终想要的样子，标记全部删掉。

执行 git add 那个文件，再执行 git commit，默认说明保存即可。

再执行 git push，这次成功。

## 用 Pull Request 合并分支

团队里大家都往 main 上直接推是不行的，得走 PR。

页面上是五步：先把分支推上去；仓库首页会出现 Compare & pull request，点它；上面选 base 为 main，下面选 compare 为 feature；填标题和说明，点 Create pull request；别人看过之后，点 Merge pull request。

base 和 compare 是 PR 里最容易搞反的一对：base 是“合到哪”，compare 是“拿哪条来合”。这里就是 feature 合到 main。

最后要注意：合并发生在 GitHub 上，你本地的 main 不会自动更新，还得 pull 一次。

## 演示十二

在 GitHub 上打开仓库，点分支下拉框切到 feature，确认刚才推上去的提交在上面。

首页会出现 Compare & pull request 的提示，点它。

base 选 main，compare 选 feature，下面能看到这次改了什么。填标题和说明，点 Create pull request，页面会跳到 PR 页面，标题下面显示 Open。

再演示 review：换一个账号打开这个 PR，点 Files changed 逐行看；点 Review changes，选 Approve 提交。

然后点 Merge pull request，状态变成 Merged。合并完点 Delete branch，这条分支从远程消失。

回到本地，切到 main 执行 git pull，刚才的改动就出现在本地了。

## 合并一个 PR 的三种方式

点 Merge 旁边的箭头，才能看到三种合并方式。

Create a merge commit：保留分支上的每一条提交，另外生成一个合并提交，和本地执行 git merge 的效果一样。

Squash and merge：把分支上的多条提交压成一条，历史干净，但分支上的过程看不到了。

Rebase and merge：把提交逐条接到 main 后面，不产生合并提交，历史是一条直线。

合并完之后页面会提示 Delete branch，把已经合掉的分支删掉，仓库才不会越堆越乱。

## 读懂一个仓库

到这儿，自己的仓库能管好了。但开源的大部分时间，其实是在读别人的仓库。

仓库本身就是说明书。想知道它是干什么的、能不能用、怎么参与，先在网页上把几个地方看一遍，比 clone 下来翻代码快得多。

第一个是 README，通常写着这个项目是做什么的、怎么安装、怎么用。

第二个是 LICENSE，它决定别人允许你拿这个项目做什么。

第三个是 CONTRIBUTING，想贡献的话要先遵守什么规矩。

再加上目录结构和最近的提交，基本就能判断这个项目大概是怎么组织的。

一句话：先读 README 决定要不要用，先读 LICENSE 决定能不能用。

## 常见的几种许可证

许可证不用背全文，但看到名字要知道大概意思。

MIT 最宽松，保留版权声明就能随便用，商业项目里见得最多。

Apache 2.0 和 MIT 接近，另外明确给了专利授权。

GPLv3 传染性最强：用了它，你改出来的东西也必须开源。

还有一种情况要注意：仓库里没有 LICENSE 文件，不等于可以随便用。没有许可证默认就是保留所有权利，只能看，不能复制和修改。

## 用 Issue 提问题

Issue 是一个仓库的公开讨论区，报 bug、提需求、问问题都在这里。

提之前先搜一下有没有人提过同样的问题，这是最基本的礼貌。

一个能被回复的 Issue，至少要写清四件事：标题用一句话说清是什么问题；复现步骤写怎么操作才会出现；期望的结果和实际的结果分别是什么；环境是哪个系统、什么版本。

这四条写全了，维护者不用追问就能动手。

## Fork：没有权限也能改

别人的仓库你没有写权限，不能直接往上推。

fork 就是把那个仓库复制一份到你自己的账号下面，那一份你想怎么改都行。

它和 clone 不是一回事：fork 发生在 GitHub 上，复制出一个属于你的远程仓库；clone 发生在你电脑上，把某个仓库下载下来。

所以通常是先 fork，再 clone 自己那份。

## 多个远程：upstream

fork 之后，本地就有两个远程了。

origin 是你自己账号下的那一份，平时往它推。

upstream 是原来的仓库，别人的更新从它来。它需要自己加：git remote add upstream，后面跟原仓库的地址。

加完之后用 git remote -v，能看到两个远程各自的地址。

想拿到原仓库的更新，先 git fetch upstream，再 git merge upstream/main，把它合进本地。

## 演示十三

在浏览器里打开一个别人的公开仓库，点右上角的 Fork，选自己的账号。等几秒钟，你账号下就出现了一个同名仓库。

把这个副本 clone 到本地，执行 git remote -v，只输出两行，都是 origin，指向你自己的仓库。

执行 git remote add upstream 加上原仓库地址，再执行 git remote -v，这次是四行：origin 两行指向你的，upstream 两行指向原仓库。

执行 git fetch upstream，再切到 main 执行 git merge upstream/main，原仓库的最新内容就合到本地。本地没动过的话，这一步会是快进。

## Pull Request：请对方收下你的改动

改完之后，要让原来的仓库收下你的改动，靠的是 Pull Request。

流程是：在你自己的仓库里改好、提交、推上去；回到原来的仓库，点 New pull request；写清改了什么、为什么改。

PR 页面会把你的改动和原仓库逐行对比出来，维护者看的就是这个页面。

所以提交说明和 PR 描述都得写清楚，不然别人不知道你想干什么。

## Code Review

维护者看完 PR，会在具体某一行上留评论。

也可能不是评论，而是要求你修改。这时不用重开 PR，改完再 push 到同一个分支就行，PR 会自动更新。

满意之后，他点 approve，再点合并。

被指出问题很正常，改完在同一个 PR 里继续讨论就好，不用觉得被冒犯。

## 演示十四

两个账号都开着：A 是原仓库的所有者，B 是来贡献的人。接着演示十三，B 已经把 A 的仓库 fork 到自己账号下、clone 到本地，也加好了 upstream。

B 在本地开一条分支 fix-typo，改一个文件、提交，push 到自己那份仓库，输出里会出现 [new branch]。

回到 GitHub，打开 B 自己那份仓库，点 New pull request。

这一步最容易出错：base repository 要选 A 的原仓库，base 分支 main；head repository 是 B 自己那份，head 分支 fix-typo。选错了 PR 就提给自己，A 根本看不到。

填标题和说明，点 Create pull request。

A 登录原仓库，打开 Pull requests，能看到这个 PR。点 Files changed 逐行看，把鼠标移到某一行点加号可以留评论。

有意见就选 Request changes 提交，PR 上会显示 Changes requested。

B 按意见改完，再 push 到同一条分支，PR 页面刷新后会自动出现新提交，不用重开。

A 再看一遍，没问题就 Approve，然后点 Merge pull request。

合并之后 B 的 fork 不会自动更新。B 回本地切到 main，执行 git fetch upstream 和 git merge upstream/main，把原仓库的改动同步过来。

## 一次完整的协作

最后把整条链路串起来。

发现问题之后，先 fork 一份，clone 到自己电脑，新建一条分支，在分支上改。

改完提交、push 上去，然后到原仓库提 PR。

维护者 review，可能需要你再改；改完通过，点击合并。

合并之后，别忘了把原仓库的更新同步回自己的 fork。

这条链路走通一次，参与开源这件事就算入门了。
