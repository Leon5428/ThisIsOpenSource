

## 回顾

在上一讲中，我们了解了操作系统的发展历史，什么是开源以及开源的意义，但是现在仍然面临着一个问题，就是如何高效地参与开源项目、管理代码， 以及与其他开发者协作。

我们知道，开源软件允许开发者查看、修改和分享源代码，但是，比如说，现在有一百名开发者正在共同开发一个软件，每个人都可能对源代码进行修改。那么，我们应该如何记录每个人的修改？如何知道某一段代码是谁修改的？如果有人修改代码之后引入了错误，我们又应该怎样恢复到之前的版本？

更进一步，如果两个人同时修改了同一个文件，我们又应该如何处理他们各自的修改？

所以说，如果仅仅是允许大家查看和修改源代码，并不足以解决这些问题。我们还需要一套有效的工具。

事实上，随着计算机和互联网的普及，软件开发的规模不断扩大，开发者之间的协作也变得越来越复杂。如何高效地管理代码、追踪修改，以及协调不同开发者的工作，逐渐成为软件开发中的重要问题。

而今天我们要介绍的 Git，就是解决这些问题的重要工具之一。

接下来，我们先来了解一下 Git 是如何诞生的。

## Git的前世今生

在正式介绍 Git 之前，我们先来了解一下 Git 的诞生背景。

最初开始开发 Linux 的时候，开发者们并没有使用专门的版本控制系统。大家交流代码、提交补丁，主要依靠电子邮件。

具体来说，来自世界各地的开发者会通过电子邮件向 Linux 的创始人 Linus Torvalds 提交自己的代码修改，Linus 则负责审查这些补丁，并将合适的修改整合到自己维护的 Linux 内核代码树中，最后再发布新的内核版本。

但是，这种开发方式存在一个非常明显的问题，那就是代码的版本管理十分困难。

例如，当一个新的 Linux 内核版本发布之后，如果我们想知道这个版本相较于上一个版本究竟修改了哪些内容，就需要借助 `diff` 这样的工具，对两个版本的代码进行比较。

而如果我们想进一步知道某一段代码是谁修改的、为什么要修改，或者希望恢复到之前的某个版本，那么整个过程就会变得更加复杂。

因此，随着软件项目的规模不断扩大，人们逐渐意识到，我们需要一种专门的工具来管理代码的历史版本，这就是版本控制系统。

版本控制系统，英文叫作 Version Control System，简称 VCS，是一种用于记录文件或项目随时间发生的变化，并对这些变化进行管理的工具。

它主要能够帮助我们完成以下几件事情：

首先，记录每一次修改。也就是说，我们可以把项目在不同时间的状态保存下来，形成一系列历史版本。

其次，查看不同版本之间的差异。例如，我们可以知道某次修改增加了哪些代码、删除了哪些代码。

第三，恢复到过去的某个版本。如果某一次修改引入了严重的错误，我们就可以利用版本控制系统找回之前的代码。

第四，追踪修改者以及修改原因。对于每一次提交，我们都可以记录是谁进行了修改，以及这次修改的目的是什么。

最后，也是对于开源项目而言非常重要的一点，就是协调多个开发者共同开发一个项目。即使不同开发者同时修改代码，版本控制系统也能够提供相应的机制，帮助他们整合各自的工作。

所以，版本控制系统实际上解决了软件开发中的一个核心问题：如何有效地管理不断变化的代码，以及如何让多个开发者共同维护同一个项目。

那么，既然版本控制系统这么重要，Linux 开发者后来使用了什么工具呢？Git 又是在什么情况下诞生的呢？

这就是我们下一页要介绍的内容。

在上一页中，我们介绍了什么是版本控制系统，以及为什么软件开发需要版本控制系统。那么，接下来我们就来看一看 Git 究竟是如何诞生的。

实际上，Git 并不是 Linux 内核开发团队使用的第一个版本控制系统。

2002 年，Linux 内核开发团队开始使用一款名为 BitKeeper 的商业分布式版本控制系统。

BitKeeper 是由 BitMover 公司开发的。当时，BitMover 公司允许 Linux 内核开发社区免费使用 BitKeeper，因此 Linux 开发者得以利用这一工具管理代码，极大地提高了开发效率。

但是，这里存在一个问题：BitKeeper 本身是一款专有软件，并不是自由软件。虽然 Linux 开发者能够免费使用它，但是他们并不能像修改 Linux 内核一样，自由地修改和分发 BitKeeper 的源代码。

到了 2005 年，BitMover 公司与 Linux 内核开发社区之间发生了矛盾，最终导致 Linux 内核开发社区失去了免费使用 BitKeeper 的权利。

这就产生了一个非常尴尬的局面：Linux 本身是世界上最著名的开源项目之一，但是开发 Linux 所依赖的版本控制工具却是一款专有软件，而且这款工具的开发公司还能够决定是否允许 Linux 社区继续使用它。

面对这样的情况，Linux 的创始人 Linus Torvalds 决定自己开发一套版本控制系统，以满足 Linux 内核开发的需求。

当然，Linus 并不是想简单地重新实现一个 BitKeeper。他希望新的版本控制系统能够支持大规模的分布式协作，具有足够高的性能，同时保证代码历史的完整性。

于是，2005 年 4 月 7 日，Git 的第一个提交诞生了。

这里值得注意的是，Git 从一开始就是为 Linux 内核这样的大型开源项目设计的，因此它非常重视性能、可靠性以及分布式开发能力。

后来，随着越来越多的开发者开始使用 Git，它逐渐发展成为今天广泛使用的版本控制系统。

顺便提一下，BitKeeper 后来也发生了一些变化。2016 年，BitKeeper 正式开源，采用 Apache 2.0 许可证。不过，到了 2020 年，BitKeeper 停止了开发。

我们就从 Git 的安装开始，一步一步学习这个工具。

## Git的安装

大家可以看到，官网右侧显示了 Git 的最新源代码发布版本，也就是 Latest source release。在它的下方有一个 Install for Windows 按钮，我们点击这个按钮，就可以进入 Windows 版本的下载页面。

点击 Install for Windows 之后，我们就进入了 Git 的下载页面。

大家可以看到，这个页面提供了很多不同的下载选项。

首先，最上方有 Windows、macOS、Linux 和 Build from Source 四个选项，分别对应不同操作系统的安装方式，以及从源代码自行构建 Git。

我们现在处于 Windows 页面，可以看到这里又提供了几个不同的版本。

首先是 Standalone Installer，也就是独立安装程序。其中，x64 Setup 适用于绝大多数使用 Intel 或 AMD 处理器的 Windows 电脑，而 ARM64 Setup 则适用于采用 ARM64 架构的 Windows 电脑。

但是我要说明的是，现在市面上绝大多数Windows笔记本电脑仍然采用Intel或AMD的x86-64处理器，使用ARM架构的Windows笔记本真的不多，可以通过在设置里面找到系统然后查看系统信息来判断自己是x86架构还是ARM64结构。

下面还有一个 Portable，也就是便携版本。它与普通安装版的主要区别在于，便携版本通常只需要解压就可以使用，不需要运行传统的安装程序。

对于我们绝大多数同学而言，直接选择Click here to download就可以了。

下载完成之后，我们双击运行 Git 的安装程序，就会进入这个界面。

大家可以看到，安装程序向我们展示了一份 GNU General Public License，也就是 GNU 通用公共许可证，简称 GPL，这里展示的是 GPL 的第二版，也就是 GPLv2。

所以，Git 本身就是一款自由软件，它的源代码是公开的，任何人都可以在遵守许可证条款的前提下使用、修改和分发 Git。

如果你没有听过第一节课，也没关系，这个GPL不会影响我们后续的操作，直接点击 Next，继续安装。

点击 Next 之后，我们就进入了 Git 安装位置的选择界面。

这里的 Select Destination Location，意思就是选择安装位置，也就是我们希望将 Git 安装到电脑的哪个文件夹中。

大家可以看到，安装程序默认选择的是 C 盘下 Program Files 文件夹中的 Git 目录。

如果大家没有特殊需求，直接使用默认的安装路径就可以了。当然，如果不希望将 Git 安装在 C 盘，也可以点击右侧的 Browse 按钮，选择其他安装位置。

另外，大家可以注意到，安装程序在下方提示我们，安装 Git 至少需要大约 342 MB 的磁盘空间。对于现在的计算机来说，这个空间占用并不算大。

这里我就不修改默认的安装位置了，直接点击 Next，继续下一步。

接下来，我们进入了 Git 安装组件的选择界面，也就是 Select Components。

首先是 Additional icons，也就是添加额外的图标。如果勾选下面的 On the Desktop，就会在桌面上创建 Git 的快捷方式。这个选项并不是必需的，大家可以根据自己的喜好选择。

接下来是 Windows Explorer integration，也就是 Windows 文件资源管理器集成。

大家可以看到，这里有两个选项，分别是 Open Git Bash here 和 Open Git GUI here。

勾选之后，我们就可以在文件夹中通过右键菜单直接打开 Git Bash 或 Git GUI。

这里我重点介绍一下 Git Bash。它是 Git for Windows 提供的一个命令行环境，我们后面学习 Git 命令时，主要就会使用这个工具。

而 Git GUI 则是一个图形化工具，可以通过图形界面完成部分 Git 操作。不过，我们这门课主要使用命令行，所以暂时不会使用它。

再往下是 Git LFS，也就是 Git Large File Storage，主要用于管理大型文件。例如，一个项目中包含大量图片、视频或者其他体积较大的文件时，就可能用到它。

下面两个 Associate 选项则与文件关联有关，分别用于关联 Git 配置文件，以及让 Shell 脚本默认通过 Bash 运行。

接下来的 Check daily for Git for Windows updates，用于每天检查 Git 是否存在新版本。

Add a Git Bash Profile to Windows Terminal，则是将 Git Bash 添加到 Windows Terminal 中，方便我们直接通过 Windows Terminal 使用 Git Bash，这个记得选上。

最后还有一个 Scalar，它是 Git 提供的一个用于管理大型代码仓库的辅助工具。对于我们现在学习的这些小型项目来说，基本不会用到，但还是选上吧，没太有影响。

总体来说，这一页虽然有很多选项，但是对于初学者而言，保持大部分默认设置就可以了。尤其是 Windows Explorer integration，我建议大家保留勾选，方便后面直接在文件夹中打开 Git Bash。

点击 Next，继续安装。

接下来，我们进入了 Select Start Menu Folder，也就是选择开始菜单文件夹。

这里需要注意，我们现在选择的并不是 Git 的安装位置，而是 Git 在 Windows 开始菜单中创建快捷方式的位置。

大家平时在 Windows 中点击开始菜单，或者直接搜索某个软件时，就可以通过这些快捷方式找到并启动对应的程序。

这里安装程序默认使用 Git 作为文件夹名称。安装完成之后，我们就可以在开始菜单中找到 Git Bash、Git GUI 等工具。

如果大家希望修改文件夹名称，可以直接在输入框中修改，也可以点击右侧的 Browse 按钮选择其他位置。

另外，左下角还有一个 Don't create a Start Menu folder，也就是不创建开始菜单文件夹。如果勾选这个选项，安装程序就不会创建对应的开始菜单文件夹。

不过，对于我们来说，没有必要修改这些设置，保持默认即可。

这里直接点击 Next，继续安装。

接下来，我们进入了 Choosing the default editor used by Git，也就是选择 Git 使用的默认文本编辑器。

首先，大家可能会有一个疑问：我们不是已经有 Git Bash 了吗？为什么还需要选择一个文本编辑器呢？

这是因为 Git Bash 只是一个命令行环境，而 Git 在执行某些操作时，还需要我们输入或修改文本内容。

例如，我们后面会学习一个叫作 git commit 的命令，它的作用是将代码的修改记录为一次提交。而每次提交时，我们通常都需要填写一段提交说明，用来解释这次修改究竟做了什么。

如果我们执行 git commit 时没有直接指定提交说明，Git 就可能自动打开默认编辑器，让我们输入这些内容。

大家可以看到，这里提供了很多编辑器，包括 Nano、Vim、Notepad++、Visual Studio Code 等。

其中，Vim 是一个非常经典的命令行文本编辑器，功能十分强大，但是对于初学者来说，它的操作方式可能不太容易理解。例如，在 Vim 中输入文字之前，我们通常需要先进入插入模式，而退出编辑器也需要使用特定的命令。

相比之下，Visual Studio Code 对大家来说应该更加熟悉。它提供了图形化的编辑界面，也更符合大多数同学平时编写代码的习惯。

因此，如果大家的电脑上已经安装了 VS Code，我比较推荐选择 Visual Studio Code 作为 Git 的默认编辑器。

当然，如果还没有安装 VS Code，也可以暂时保留默认的 Vim，或者选择其他已经安装的编辑器。这个设置并不是永久不变的，安装完成之后，我们仍然可以通过 Git 的配置命令进行修改，这里选择nano，因为这个操作起来比较简单，然后点击 Next，继续安装。

接下来，我们进入了 Adjusting the name of the initial branch in new repositories，也就是设置新建仓库的初始分支名称。

首先，我们需要简单了解一下什么是分支。

大家可以暂时把分支理解为项目的一条独立开发线路。例如，在开发一个软件的时候，我们可能希望一部分开发者负责添加新功能，另一部分开发者负责修复错误。那么，我们就可以让他们在不同的分支上进行开发，最后再将各自的修改合并起来。

当然，这里只是一个简单的解释，关于分支的具体工作原理和使用方法，我们会在后面专门介绍。

现在大家只需要知道，当我们使用 Git 创建一个新的仓库时，Git 通常会为这个仓库设置一个初始分支名称。

这里有两个选项。

第一个是 Let Git decide，也就是让 Git 自己决定初始分支的名称。在当前安装程序中，这个名称是 master。

第二个是 Override the default branch name for new repositories，也就是由我们自己指定新仓库的初始分支名称。

大家可以看到，这里填写的是 main。

实际上，master 和 main 都只是分支的名称，并没有本质上的功能区别。早期 Git 通常使用 master 作为默认分支名称，而现在很多开源项目和代码托管平台，包括 GitHub，都更倾向于使用 main。

因此，我建议大家选择第二个选项，将初始分支名称设置为 main，这样也更符合目前很多开源项目的使用习惯。

需要注意，这个设置只会影响以后新建的仓库，不会修改已经存在的仓库。

这里我们选择第二项，保持 main 不变，然后点击 Next，继续安装。

接下来，我们进入了 Adjusting your PATH environment，也就是配置 Git 的 PATH 环境变量。

首先，我们需要简单了解一下什么是 PATH。

大家平时在命令行中输入一条命令时，例如 git，操作系统需要知道这个命令对应的可执行程序究竟存放在哪里。

而 PATH 就是一个环境变量，它记录了一系列目录。当我们在命令行中输入某个命令时，系统就可以根据 PATH 中记录的目录，查找对应的可执行程序。

这里安装程序提供了三个选项。

第一个是 Use Git from Git Bash only，也就是只允许我们在 Git Bash 中使用 Git。选择这一项不会修改 Windows 的 PATH 环境变量，因此我们通常无法直接在 PowerShell 或 CMD 中使用 Git 命令。

第二个是 Git from the command line and also from 3rd-party software，也就是允许我们在命令行以及第三方软件中使用 Git。

选择这一项之后，安装程序会将 Git 所需的相关目录添加到 PATH 环境变量中。这样一来，我们不仅可以在 Git Bash 中使用 Git，还可以在 Windows 的 CMD、PowerShell，以及 VS Code 等开发工具中调用 Git。

这也是安装程序推荐的选项。

第三个是 Use Git and optional Unix tools from the Command Prompt。除了 Git 之外，它还会将一些 Unix 工具添加到 Windows 的 PATH 中，例如 find 和 sort。

但是，这里存在一个问题：Windows 本身也提供了同名的命令。如果我们将这些 Unix 工具添加到 PATH 中，就可能导致命令名称冲突，使某些程序的运行结果与预期不同。

因此，对于绝大多数同学来说，我建议选择第二个选项。

这样既能够方便我们在不同的终端和开发工具中使用 Git，又可以避免引入不必要的命令冲突。

这里我们保持第二项不变，点击 Next，继续安装。
